1. BIG PICTURE — WHAT WE BUILT AND HOW THE PIECES CONNECT
================================================================================

The application is a 3-tier stack:

    Browser (Next.js frontend)
        |
        |  port 3000  (customer chat + agent dashboard)
        v
    Next.js server (frontend container, "frontend")
        |  internal Docker network, http://api:8000
        v
    FastAPI backend (api container, "api")
        |  psycopg + IPv6  -> Supabase Postgres (hosted)
        |  qdrant-client   -> Qdrant Cloud (hosted)
        |  ChatOpenAI      -> OpenRouter (LLM)
        |  langsmith       -> LangSmith (tracing)
        |  HuggingFace     -> embedding model download (all-MiniLM-L6-v2)

Deployment model chosen (with the user):
    - Build BOTH images on the local machine.
    - Tag and push them to Docker Hub (public repos under namespace "akr6723").
    - On a single EC2 instance, run `docker compose up` using an image-based
      compose file (docker-compose.prod.yml). The EC2 pulls the images from
      Docker Hub and runs the containers on the same Docker network.

Key architectural facts that drove every decision:

  a) The Next.js frontend makes TWO kinds of API calls:
       - Server-side rewrites for /chat, /tickets, /escalations  -> BACKEND_API_URL
       - Browser-side (client JS) calls for /auth/login, /auth/register, /auth/me
         -> NEXT_PUBLIC_BACKEND_API_URL
     NEXT_PUBLIC_* values are INLINED INTO THE JS BUNDLE at `next build` time.
     That means the EC2 public IP had to be known BEFORE building the frontend
     image, and changing the domain later forces a frontend rebuild.

  b) /auth/* is NOT covered by the Next.js rewrites (frontend/next.config.mjs),
     so the browser talks to the FastAPI container DIRECTLY on port 8000.
     Cross-origin => CORS must allow the frontend origin. The app reads
     CORS_ALLOWED_ORIGINS at startup (app/main.py) — we set it in prod .env.

  c) The Supabase DATABASE_URL hostname resolves ONLY to IPv6 (AAAA record).
     This single fact caused the biggest detour of the session (see section 3.10).

  d) The backend warms up by downloading the HuggingFace embedding model at
     startup (app/main.py warmup handler) -> the EC2 needs outbound internet.

3.2 Backend image build (first attempt — the 9.18 GB problem)
--------------------------------------------------------------------------------
Command:
    docker build -t akr6723/support-ai-api:1.0.0 -t akr6723/support-ai-api:latest .

Result: image built, but it was 9.18 GB.
Root cause (visible in the build log): requirements.txt pins
sentence-transformers>=2.2.0 which depends on torch>=1.11.0. pip resolved
torch 2.13.0, and on Linux the default torch wheel now bundles the FULL CUDA
runtime. The build downloaded nvidia-cudnn, nvidia-nccl, nvidia-cublas,
nvidia-cusolver, triton, etc. (~5.5 GB of unused packages), because the app only
runs embeddings on CPU.

Why it matters: the EC2 would have to pull 9.18 GB, and on a 20 GB disk that is
wasteful and slow.

We asked the user; they chose "Shrink image with CPU torch (Recommended)".

--------------------------------------------------------------------------------
3.3 Dockerfile fix — CPU-only torch -> 2.64 GB
--------------------------------------------------------------------------------
Edited root Dockerfile. Before the requirements install we added:

    RUN pip install --no-cache-dir torch --index-url https://download.pytorch.org/whl/cpu
    RUN pip install --no-cache-dir -r requirements.txt

Mechanics: installing torch from the CPU index first means the wheel is
torch-2.13.0+cpu (191.8 MB). When pip later resolves sentence-transformers'
torch>=1.11.0 requirement, the already-installed CPU torch satisfies it, so pip
does NOT pull the CUDA build from PyPI.

Rebuilt: `docker build -t akr6723/support-ai-api:1.0.0 -t akr6723/support-ai-api:latest .`
New image size: 2.64 GB. (Also tagged 1.0.1 later for the threshold fix —
see 3.12. Final running tag: 1.0.1.)

      the public address the browser must reach.

3.10 The IPv6 saga (Supabase direct connection) — 3 layers of fixes
--------------------------------------------------------------------------------
PROBLEM: when running migrations we got
    psycopg.OperationalError: ... connection to server at
    "2406:da14:1772:ea01:995a:e8ba:6d59:da2c", port 5432 failed:
    Network is unreachable

DIAGNOSIS (getent ahosts on the EC2):
    db.okvnguvhukxwodknuwww.supabase.co -> IPv6 ONLY (single AAAA record,
    no A record). The local dev machine had IPv6; the EC2 had none, and
    Supabase's direct-connection hostname is IPv6-only. (This is a known
    Supabase behavior. AGENTS.md mandates the direct connection, not the
    IPv4 pooler.) The user chose "Enable IPv6 on EC2".

THREE SEPARATE LAYERS all needed fixing — this is the subtle part:

  LAYER 1 — the EC2 network itself (AWS Console):
    * VPC  vpc-0c803114bd1a5272e  -> Actions -> Edit CIDRs -> Add IPv6 CIDR
      (Amazon-provided)
    * Subnet subnet-0f786e0e6cdc5656e -> Edit IPv6 CIDRs -> add the /64
      AND enable "Auto-assign IPv6 address" on the subnet
    * Route table -> add ::/0 -> Internet Gateway
    * Instance -> Networking -> Manage IP addresses -> Assign new IPv6 address
    Verified: instance got 2600:1f18:62f:dd00:ba34:5c98:72d1:9eb1,
    `curl -6 https://www.google.com` -> 200, and a raw TCP test to
    2406:da14:...:5432 succeeded FROM THE HOST.

  LAYER 2 — the Docker DAEMON (default bridge):
    After Layer 1, one-off `docker run` tests STILL failed. Reason: the Docker
    default bridge network is IPv4-only by default. Fix:
        echo '{"ipv6": true, "fixed-cidr-v6": "fd00:1:1:1::/64"}' \
             | sudo tee /etc/docker/daemon.json
        sudo systemctl restart docker
    Docker >= 25 performs NAT66 automatically, so containers get outbound IPv6
    through the host's global address. Verified inside a container:
        DB-TCP-OK to the Supabase IPv6:5432.

  LAYER 3 — the COMPOSE network (user-defined bridge):
    The compose stack runs on its own network "support-ai_default", which had
    been created BEFORE IPv6 was enabled, so it was IPv4-only even though the
    daemon now supported IPv6. That is why the API container still said
    "Network is unreachable" while a fresh `docker run` worked.
    Fix (in docker-compose.prod.yml):
        networks:
          default:
            enable_ipv6: true
    Then `docker compose -f docker-compose.prod.yml down` (removes the old
    network) and `up -d` (recreates it with IPv6). Verified:
        docker network inspect support-ai_default -> EnableIPv6: true,
        IPv6 subnet fddd:68ac:b6cf::/64, container got fddd:68ac:b6cf::2.
    (If the network had been created after the daemon change, just `up` would
    have been enough — but `down` guarantees a fresh network.)

After all three layers: register/login/chat smoke tests passed.

  POST /auth/register  -> access_token

4. HOW ENVIRONMENT VARIABLES ARE PASSED (FULL MECHANICS)
================================================================================

There are FOUR distinct paths for configuration in this deployment:

  (1) BUILD-TIME build args -> baked into the frontend image:
        ARG BACKEND_API_URL / ARG NEXT_PUBLIC_BACKEND_API_URL
      Values were supplied on the `docker build` command line. The Next.js
      compiler inlines NEXT_PUBLIC_* into the JS bundle (AuthContext.tsx) and
      next.config.mjs reads BACKEND_API_URL when assembling the standalone
      server. These are FIXED once built — they cannot be changed at runtime
      without rebuilding the image. This is why the EC2 IP had to be known
      before the frontend build.

  (2) RUNTIME env_file (api service only):
        env_file: - .env    (docker-compose.prod.yml)
      Compose reads /opt/support-ai/.env line by line (KEY=value, no spaces)
      and injects every variable into the api container's process environment.
      The container's Python then reads them in app/config.py via os.getenv().
      This is where ALL secrets live: DATABASE_URL, QDRANT_*, OPEN_ROUTER_*,
      JWT_SECRET, HF token, LangSmith keys, CORS_ALLOWED_ORIGINS.
      IMPORTANT: these are NOT baked into the image — .env is in .dockerignore
      for both builds, so the image layers contain no secrets. The .env file
      exists only on the EC2 (and as .env.prod, gitignored, on the machine).

  (3) RUNTIME environment (frontend service):
        environment: BACKEND_API_URL: http://api:8000
      Passed directly in the compose file. The Next standalone server reads it
      per request for the server-side rewrites (it also got the build-time
      value, but this runtime value wins for the running server).

  (4) Process environment of one-off containers:
        docker run --rm --env-file .env akr6723/support-ai-api:1.0.1 python ...
      Used for migrate/seed/ingest so the one-time scripts hit the same prod
      DB/Qdrant with the same credentials as the running API.

Other important env-related notes:
  - app/config.py has sane defaults for everything not supplied
    (JWT_ALGORITHM HS256, JWT_EXPIRY_HOURS 24, QDRANT_COLLECTION
    knowledge_base, EMBEDDING_MODEL all-MiniLM-L6-v2, CHUNK_SIZE 500,
    CHUNK_OVERLAP 50, LLM_MODEL gpt-4o-mini, OPEN_ROUTER_BASE_URL
    https://openrouter.ai/api/v1, LLM_TEMPERATURE 0.0, LLM_MAX_TOKENS 1024,
    CONFIDENCE_THRESHOLD 0.7, RETRIEVAL_SCORE_THRESHOLD 0.40,
    ESCALATION_ACKNOWLEDGMENT default text, LANGSMITH_TRACING false).
  - CORS_ALLOWED_ORIGINS is read in app/main.py; if absent it falls back to
    localhost:3000/3001 — which is why we HAD to set it for the EC2 origin.
  - The original .env used `KEY = value` (spaces). Docker's env-file parser
    rejects that; we normalized to `KEY=value`.
